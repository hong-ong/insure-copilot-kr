# AI 기획자 8주 커리큘럼

Sep 30, 2026 · @정재홍

> 원본은 claude.ai 프로젝트 문서 「AI PM 완성 8주 과정」. 원본을 고치면 이 파일도 함께 갱신한다.

8주 뒤 결과물은 '보험 약관·규정 AI 어시스턴트' 하나입니다. 매주 한 주제를 배우고, 같은 프로젝트에 기능 하나와 기획 문서 하나를 더해 마지막 주에 케이스 스터디·데모·코드 저장소로 묶습니다.

## 최종 결과물

8주 뒤 손에 쥐는 것은 동작하는 서비스 하나와, 그 서비스를 기획자 관점에서 풀어낸 케이스 스터디입니다. 가상의 보험사 사내 AX팀이 설계사·상담원을 위해 만드는 어시스턴트라고 가정하고, 두 종류의 질문을 받습니다.

- **약관·규정 질문 (RAG):** "실손보험에서 도수치료는 어떻게 보장되나요?" → 표준약관·보험업법 조문과 분쟁조정사례를 근거로 답하고 출처를 표시합니다. "이 고객은 보험금을 받을 수 있나요?"처럼 판단을 요구하면 근거 조문만 안내하고 판단은 거절합니다.
- **지표 질문 (GenBI):** "이번 분기 강남지점 설계사 보수교육 이수율과 13회차 유지율은?" → 설계사·계약 데이터 마트에서 미리 정의한 지표로 계산합니다. 질문자의 권한에 따라 볼 수 있는 범위가 달라집니다.

이 주제를 고른 이유는 네 가지입니다.

- 공개 문서가 두텁습니다. 보험업법·감독규정, 표준약관(보험업감독업무시행세칙 별표15), 금감원 보험 분쟁조정사례 160건이 공개돼 있습니다.
- 약관은 길고 특약·별표·표가 많아 파싱·검색 실력을 보여주기 좋고, "판단은 거절" 설계까지 보여줄 수 있습니다.
- 보험사들이 청구·심사·영업 지원에 AI를 내재화하는 중이라 현업 문제와 바로 맞닿습니다.
- 제안서의 AI 튜터·GenBI·게이트웨이 구조와 교육 도메인 경험을 공개 데이터로 다시 구현합니다. 설계사는 등록 후 2년마다 보수교육 의무가 있어 교육 지표가 자연스럽게 들어갑니다. 제안서 자료 자체는 쓰지 않습니다.

## 시스템 구조

```
질문 → 라우터(의도 분류)
          ├─ 약관·규정 RAG ─┐
          ├─ GenBI ─────────┼─→ 답변 검증(근거 없음·판단성이면 거절) → 사용자
          └─ 거절 ──────────┘
공통 층: LLM 게이트웨이(LiteLLM) · 트레이스(Langfuse) · 골든셋 회귀 평가
데이터 층: 법규·표준약관·분쟁사례·가상 사내 문서(벡터DB) / 설계사·계약 마트(DuckDB)
```

라우터가 질문을 약관·규정 RAG, GenBI, 거절 중 하나로 보내고, 어느 길이든 답변 검증을 통과해야 사용자에게 돌아갑니다. 게이트웨이·트레이스·골든셋은 모든 호출이 거치는 공통 층입니다.

## 8주 로드맵

| 단계 | 주차 | 내용 | 관문 |
| --- | --- | --- | --- |
| 정의 | 1–2 | 문제 정의, 데이터·파싱, PRD | 조·항 단위 청크 + PRD v1 |
| RAG | 3–5 | 첫 RAG, 골든셋, 평가, 개선 실험 | 베이스라인 수치 확정 → 채택 구성 확정 |
| 확장 | 6–7 | GenBI, 에이전트 통합, 권한·운영 | 통합 골든셋 재평가 + 기능 동결 |
| 공개 | 8 | 배포, 케이스 스터디, 영상 | — |

1–2주에 무엇을 만들지 정하고, 3–5주에 RAG를 만들어 수치로 개선하고, 6–7주에 GenBI와 에이전트로 넓힌 뒤 8주차에 공개합니다. 관문 기준을 못 채우면 다음 단계로 넘어가지 말고 그 주를 연장하세요.

**개발 환경**

- Python 3.12 + uv, VS Code 또는 Cursor, Git·GitHub
- 코딩 에이전트: Claude Code 또는 Cursor. FDE·AX 매니저 공고가 요구하는 역량이기도 합니다.
- LLM: Gemini API 또는 OpenRouter를 [LiteLLM](https://www.litellm.ai/)로 묶어 호출
- 임베딩: bge-m3, KURE (로컬 실행, CPU도 가능)
- 로컬 LLM(선택): Ollama. GPU 메모리가 부족하면 건너뛰어도 커리큘럼에 지장이 없습니다.
- 벡터DB: Chroma로 시작, 여유 있으면 Qdrant 또는 pgvector
- 평가·관측: Langfuse, RAGAS
- 정보계: DuckDB (도전: dbt + MetricFlow)
- 화면: Streamlit

**AI 코딩 도구 사용 규칙**

1. 코드는 AI가 써도 됩니다. 다만 커밋 전에 함수마다 "무엇을 왜 하는가"를 한 문장으로 직접 적습니다. 면접에서 코드 설명을 요구받습니다.
2. 매주 한 부분은 AI 없이 직접 작성합니다. 각 주차에 표시해 두었습니다.
3. 막히면 30분은 혼자 붙잡고, 그다음 AI나 검색을 씁니다.
4. 모든 실험은 학습 로그에 날짜 · 가설 · 결과 · 배운 점으로 남깁니다. 8주차 케이스 스터디의 재료가 됩니다.

비용은 무료 한도와 로컬 임베딩으로 시작할 수 있습니다. 4주차부터 평가를 반복 실행하므로, LiteLLM 비용 로그를 매주 확인하세요.

## 1주차 — 문제 정의와 개발 환경

**목표:** 무엇을 왜 만드는지 한 장으로 설명하고, 코드로 LLM을 호출할 수 있다.

**공부**

- LLM 기초: 토큰, 컨텍스트 윈도, 임베딩, temperature, 할루시네이션이 생기는 이유
- RAG 전체 흐름(수집 → 파싱 → 청킹 → 임베딩 → 검색 → 생성 → 평가): [RAG 비법노트: RAG 시작하기](https://wikidocs.net/book/16865) 무료 공개분
- 보험 도메인 기초: 주계약과 특약, 실손보험 세대별 차이, 약관의 관·조·항 구조 — [금감원 보험 표준약관](https://www.fss.or.kr/fss/bbs/B0000115/view.do?nttId=21943&menuNo=200504&pageIndex=)을 훑어보며 익힙니다.
- AI PM 관점: 결과가 확률적인 제품의 특징, 평가가 왜 기획 업무인가 — [AI PM 2026 로드맵 (요즘IT)](https://yozm.wishket.com/magazine/detail/3575/)

**실습**

- GitHub 저장소 만들고 uv로 Python 환경 구성
- LiteLLM으로 클라우드 모델 1개와 (선택) Ollama 로컬 모델 1개 호출
- 베이스라인 0: 실손의료보험 표준약관 하나를 통째로 프롬프트에 넣고 질문해 봅니다. "RAG 없이도 되나?"에 답할 비교 기준입니다.
- [국가법령정보 공동활용 Open API](https://open.law.go.kr/LSO/openApi/guideList.do) 신청. 승인을 기다려야 할 수 있으니 첫날 처리합니다.
- 직접 작성: LLM 호출 스크립트 (모델·프롬프트·응답 시간 출력)

**기획 산출물**

- 문제 정의서 (1–2p): 누가, 어떤 상황에서, 지금 어떻게 해결하고, 무엇이 불편한가
- 페르소나 3명: 설계사(고객 상담 중 약관 확인), 콜센터 상담원(보장 범위 문의 응대), 본사 교육·준법 담당자(지표 확인)
- 사용 시나리오 10개와 예상 질문 30개 초안. 3주차 골든셋의 씨앗이 됩니다.
- 대체재 분석: 약관 PDF에서 Ctrl+F, 본사 상품지원팀 문의, ChatGPT 직접 사용, 상용 솔루션 각각의 한계

**포트폴리오 반영:** 케이스 스터디 2장 "문제와 사용자" 초안

## 2주차 — 데이터 확보, 문서 파싱, PRD

**목표:** 약관·법규·분쟁사례를 조·항 단위의 깨끗한 데이터로 만들고, 무엇을 만들지 PRD로 확정한다.

**공부**

- 문서 파싱: 텍스트 PDF와 스캔 PDF의 차이, 표 추출, HWP·HWPX 구조 — [HWP 파싱이 까다로운 이유 (한컴)](https://blog.hancom.com/hwp-word-document-parsing-json/)
- 청킹 전략: 고정 길이, 문장 단위, 조·항 단위, 부모-자식(parent-child). 약관은 본문·특약·별표를 따로 다뤄야 합니다.
- 메타데이터 설계: 문서 종류(법규·약관·사례·사내), 조문 번호, 담보명, 약관 적용 기간(버전), 출처 URL, 공개 범위

**실습**

- 데이터 범위 확정
  - 법규: 보험업법·시행령, 보험업감독규정, 금융소비자보호법의 설명의무 부분 (Open API)
  - 약관: 실손의료보험·질병상해보험·생명보험 표준약관 (보험업감독업무시행세칙 별표15)
  - 사례: [금감원 보험 분쟁조정사례](https://www.mt.co.kr/finance/2026/01/29/2026012814203220724) (담보별로 공개)
  - 가상 사내 문서 3–5개: 설계사 영업 가이드, 상품지원 FAQ, 준법 체크리스트. 공개 범위(전사·지점장 이상)를 붙여 7주차 권한 테스트에 씁니다.
- [Docling](https://github.com/docling-project/docling)으로 PDF를, [HWP 파서](https://github.com/ureca-corp/document_parser)로 HWP를 마크다운·JSON으로 변환
- 조·항 단위 청크와 메타데이터를 JSON으로 저장하고, 샘플 20개를 원문과 대조 검수. 특히 보장 한도 표가 깨지지 않았는지 확인합니다.
- 개인정보 마스킹 규칙: 주민번호·연락처·계좌번호 정규식에 더해, 보험에서는 병력·진단명 같은 건강정보(민감정보)도 대상입니다. 제안서의 문서 품질 관리 아이디어를 재현하는 부분입니다.
- 원문 파일은 저장소에 올리지 않고, 다운로드 스크립트와 출처 목록만 남깁니다.
- 직접 작성: 관·조·항 번호를 뽑는 정규식과 청크 스키마

**기획 산출물**

- PRD v1: 목표·비목표, 기능 요구사항, 비기능 요구사항(응답 3초 이내, 출처 필수, 약관 버전 명시, 판단 요구 시 거절과 담당 부서 안내), 범위 밖 정의
- 성공 지표: 핵심(정답률, 출처 정확도)과 가드레일(근거 없는 답변 비율, 판단 요구에 답한 비율, p95 응답시간, 질의당 비용)
- 데이터 명세서: 소스별 형식, 갱신 주기, 메타데이터 스키마, 약관 버전 관리 규칙, 파싱 품질 기준

**포트폴리오 반영:** 3장 "PRD와 성공 지표", 4장 "데이터와 파싱"

## 3주차 — 첫 RAG와 골든셋

**목표:** 질문하면 출처와 함께 답하는 최소 버전을 띄우고, "정답"을 정의한 골든셋을 만든다.

**공부**

- 임베딩과 벡터 검색: 코사인 유사도, top-k, 벡터DB의 역할
- LangChain 기본 구성(로더 → 스플리터 → 임베딩 → 벡터스토어 → 리트리버 → 체인) — [LangChain 한국어 튜토리얼 (테디노트)](https://github.com/teddylee777/langchain-kr)
- 인용 강제 프롬프트: 근거 조문 ID가 없으면 답하지 않기, 판단 요구는 거절하기

**실습**

- 벡터 검색만 쓰는 단순 RAG: bge-m3 임베딩 + Chroma + LLM
- Streamlit 화면: 질문 입력 → 답변 + 근거 조문(문서명·조항·약관 버전) 표시
- 골든셋 v1 50문항 작성: 질문, 기대 답, 근거 조문 ID, 유형, 난이도
  - 약관 조회 15 · 법규 조회 10 · 여러 조문 종합 10 · 분쟁사례 기반 5 · 판단 요구·범위 밖(거절이 정답) 10
  - 실제 설계사·고객 말투로 쓰고, "실비", "도수" 같은 줄임말과 모호한 질문도 넣습니다.
- 직접 작성: 골든셋 50문항 (AI로 초안을 만들어도 정답과 근거는 약관을 직접 확인)

**기획 산출물**

- 골든셋 설계서: 유형 정의, 작성 원칙, 채점 기준, 합격선

**포트폴리오 반영:** 5장 "품질 기준"의 앞부분, 데모 첫 화면

## 4주차 — 평가 체계와 에러 분석

**목표:** 현재 성능을 숫자로 확정하고, 실패를 유형별로 분류해 개선 우선순위를 정한다. AI 기획자 포트폴리오에서 가장 중요한 주입니다.

**공부**

- 평가 방법: 코드 기반 평가와 LLM-as-judge, 사람 판정과의 일치율 확인 — [AI Evals FAQ (Hamel Husain·Shreya Shankar)](https://hamel.dev/blog/posts/evals-faq/)
- 에러 분석: 실패 사례마다 자유 메모를 달고(open coding), 비슷한 것끼리 유형으로 묶기(axial coding). 이 작업을 PM이 직접 해야 한다는 게 이 방법론의 핵심입니다.
- 트레이싱·관측성: [Langfuse LLM-as-a-Judge](https://langfuse.com/docs/evaluation/evaluation-methods/llm-as-a-judge), [Langfuse + RAGAS 예제](https://github.com/langfuse/langfuse-docs/blob/main/cookbook/evaluation_of_rag_with_ragas.ipynb)

**실습**

- 평가 스크립트: Recall@5·MRR은 직접 계산, Faithfulness는 RAGAS
- Langfuse 연결: 질의별 검색 결과·프롬프트·응답·지연시간·비용 기록
- 골든셋 전체 실행 → 실패 사례를 전부 읽고 메모 → 실패 유형표. 보험에서 자주 나올 유형은 이런 것들입니다.
  - 약관 버전(실손 세대) 혼동, 특약 누락, 보장 한도 표 깨짐
  - 의료 용어·줄임말 불일치("실비" vs "실손의료비")
  - 근거 없이 답함, 판단 요구에 답함, 반대로 답해야 할 때 거절함
- LLM 심판 결과 20건을 직접 채점해 일치율 확인 (심판을 믿어도 되는지 검증)
- 직접 작성: Recall@5·MRR 계산 함수

**기획 산출물**

- 베이스라인 평가 리포트: 지표별 점수, 실패 유형 Top 5와 비율, 대표 사례
- 개선 백로그: 실패 유형별 가설을 영향도 × 난이도로 우선순위화

**포트폴리오 반영:** 5장 "품질 기준" 완성, 6장 "실험과 결정"의 출발점

**완료 체크**

- [ ] 실패 유형표·개선 백로그

## 5주차 — 검색 품질 개선 실험

**목표:** 4주차 백로그의 가설을 실험하고, 전후 수치로 구성안을 결정한다.

**공부**

- 키워드 검색 BM25와 한국어 형태소 분석(Kiwi) — [한글 형태소 분석기 + BM25 검색기](https://wikidocs.net/234009)
- 하이브리드 결합(RRF, 가중합), 리랭커(bge-reranker-v2-m3), 질의 재작성(multi-query, HyDE)
- 임베딩 선택: bge-m3 vs KURE vs Qwen3-Embedding — [임베딩 모델 선택 가이드](https://www.data-dynamics.io/ko/blog/embedding-model-guide)

**실습 — 실험 매트릭스** (한 번에 변수 하나만 바꿉니다)

| 실험 | 비교안 | 보는 지표 |
| --- | --- | --- |
| E1 청킹 | 고정 500자 vs 조·항 단위 vs 부모-자식 | Recall@5 |
| E2 임베딩 | bge-m3 vs KURE (+ Qwen3-Embedding 선택) | Recall@5, MRR |
| E3 검색 방식 | 벡터 vs BM25 vs 하이브리드 | Recall@5, MRR |
| E4 용어 사전 | 질의 그대로 vs 보험 동의어 사전으로 재작성 ("실비" → "실손의료비") | Recall@5 |
| E5 리랭커 | 하이브리드 vs 하이브리드 + 리랭커 | MRR, p95 지연 |
| E6 생성 | 인용 검증·거절 임계값 적용 전후 | Faithfulness, 거절 정확도 |

실패한 실험도 그대로 기록합니다. 한국어 법률 RAG 예제에서는 RRF 하이브리드가 Recall을 28%에서 24%로 오히려 낮춘 사례도 있습니다 ([law-agent](https://github.com/bbungjin/law-agent)). 이런 결과와 이유 분석이 면접에서 가장 강한 재료입니다.

- 직접 작성: 보험 동의어 사전 30개 (골든셋 실패 사례에서 뽑기)

**기획 산출물**

- 실험 설계서: 가설 · 변수 · 측정 방법 · 판정 기준 (예: Recall@5가 5%p 이상 오르면 채택)
- 실험 결과 리포트: 전후 비교표, 비용·지연시간 트레이드오프
- 의사결정 기록(ADR) 3건: 왜 이 청킹·임베딩·검색 조합인가

**포트폴리오 반영:** 6장 "실험과 결정" — 케이스 스터디의 하이라이트

**완료 체크**

- [ ] 실험 6개 실행과 결과표
- [ ] 채택 구성 확정, 골든셋 재평가
- [ ] p50·p95 응답시간 측정
- [ ] ADR 3건

## 6주차 — 정보계와 GenBI

**목표:** 설계사·계약 데이터 마트를 스타 스키마로 만들고, 정의된 지표 위에서 자연어 질문에 답한다. 정보계를 "읽고 설계할 수 있는 기획자"임을 증명하는 주입니다.

**공부**

- SQL: SELECT·JOIN·GROUP BY·CASE, 윈도 함수 맛보기. DuckDB로 바로 실습합니다.
- 차원 모델링: 팩트·디멘전, 그레인(한 행이 무엇인가), 스타 스키마
- 시맨틱 레이어: 지표를 한 번 정의해 모두가 같은 숫자를 보게 하는 층 — [dbt: Semantic Layer vs Text-to-SQL 2026](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026)
- Text-to-SQL의 위험: 틀려도 그럴듯한 숫자를 내놓는다는 점

**실습**

- 가상 데이터 생성(Python Faker): 설계사 300명, 지점 10개, 계약 1만 건, 1년치 보수교육 이수 기록
- 스타 스키마
  - 팩트: fact_contract(계약 1건 = 1행: 월납보험료, 13회차 유지 여부, 청약철회·불완전판매 여부), fact_training(교육 이수 1건 = 1행)
  - 디멘전: dim_agent(지점, 전속·GA 채널, 경력, 등록일), dim_product(실손·질병·종신 등), dim_date
- 지표 5개 정의: 보수교육 이수율, 13회차 유지율, 불완전판매비율, 청약철회율, 설계사 1인당 신계약 건수. 업계 지표는 협회 공시 정의를 찾아 그대로 옮깁니다. 이 조사 자체가 기획 업무입니다.
- 기본안: 지표 YAML(정의·계산식·허용 차원)을 만들고, LLM은 지표와 차원만 고르고 SQL은 템플릿이 만듭니다.
- 도전안: [dbt + MetricFlow](https://www.getdbt.com/blog/open-source-metricflow-governed-metrics) (2025년 12월 Apache 2.0으로 오픈소스화) — [DuckDB 샌드박스 예제](https://github.com/MarkPhamm/duckdb-dbt-metricflow)
- 지표 질문 20문항으로 raw Text-to-SQL과 시맨틱 레이어를 비교: 정답률, "틀린 숫자" 건수, "답 못함" 건수. "보수교육 미이수 설계사의 불완전판매비율은?"처럼 팩트 두 개를 잇는 질문을 꼭 넣습니다.
- 직접 작성: 지표 5개의 SQL (정답지 역할)

**기획 산출물**

- 지표 정의서: 이름, 비즈니스 정의, 계산식, 그레인, 필터, 소유 부서
- ERD (스타 스키마 그림)
- 행 단위 권한 정책: 설계사는 본인 실적만, 지점장은 자기 지점만, 본사 교육·준법 담당은 전사

**포트폴리오 반영:** 7장 "정보계와 GenBI"

**완료 체크**

- [ ] DuckDB 마트 적재

포트폴리오는 기능 목록이 아니라 "문제 → 품질 기준 → 실험 → 결정 → 결과"의 이야기로 짭니다. AI 기획자 채용에서 차별점은 데모 자체보다 평가와 의사결정의 근거입니다.

형태는 세 가지입니다. GitHub README는 개발자 면접관용, 케이스 스터디(노션 또는 PDF)는 기획·PM 면접관용, 3분 영상은 모두를 위한 입구입니다.

| 케이스 스터디 장 | 담을 내용 | 가져올 산출물 |
| --- | --- | --- |
| 1. 한 장 요약 | 문제, 해결, 핵심 수치 3개 | 8주차 |
| 2. 문제와 사용자 | 페르소나, 시나리오, 대체재의 한계 | 1주차 |

| 4. 데이터와 파싱 | 약관 구조·버전 처리, 파싱 검수 결과 | 2주차 |

**이력서 문장 예시** (○○은 실제 측정값으로 채웁니다)

- 보험 약관·규정 AI 어시스턴트 기획·구현(개인 프로젝트): 약관·규정 50, 지표 20문항 골든셋과 평가 지표를 설계하고 반복 평가 체계 구축
- 하이브리드 검색·보험 용어 사전·리랭커 등 6개 실험으로 Recall@5 ○○% → ○○%, 근거 없는 답변 ○○% → ○○% 개선
- 설계사·계약 데이터 스타 스키마와 지표 5종을 정의해 시맨틱 레이어 기반 자연어 질의 구현, 틀린 숫자 응답 ○○건 → ○○건

**면접에서 나올 질문**

- 청킹을 왜 조·항 단위로 했나요? 특약과 별표는 어떻게 처리했나요?

- LLM 심판은 어떻게 믿었나요?
- RAG 대신 약관을 통째로 넣으면 안 되나요? (1주차 베이스라인 0이 답입니다)
- 실패한 실험과 거기서 배운 점은?
- 보험사에 실제로 도입한다면 망분리·AI 기본법·설명의무·건강정보는 어떻게 다루시겠어요?
- 질의당 비용과 응답시간은요?

**제안서 경험을 다루는 원칙**

- 원본과 도식은 싣지 않고 본인 역할만 씁니다. 제안서 모든 페이지에 저작권 표기가 있습니다.
- "제안서에서 설계한 하이브리드 검색·시맨틱 레이어·골든셋 운영을 이번에 직접 구현하고 수치로 검증했다"는 연결로 서술합니다.
- 제안서의 기대효과 수치는 쓰지 않고, 직접 측정한 수치만 씁니다.

주차별 학습 노트와 실험 표를 저장소에 함께 둔 한국어 법률 RAG 예시([law-agent](https://github.com/bbungjin/law-agent))를 README 구성의 참고로 보세요.
